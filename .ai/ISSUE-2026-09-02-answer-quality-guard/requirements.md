# 工作流答案质量防护需求

## 背景

股票分析工作流会把多个工具结果交给模型生成 Markdown 答案。一次真实请求中，行情、技术、财务和新闻任务均成功，但模型在生成表格时进入管道符、分隔符和反引号的重复退化，MongoDB 最终保存了被截断的非法 Markdown。前端使用标准 GFM 渲染器，只能原样展示这些异常字符。

更换更强模型可以降低发生概率，但无法消除长上下文、格式退化和输出截断风险，因此需要与模型无关的后端质量防线。

## 目标

1. 工作流最终答案使用独立、无会话记忆的生成入口，避免内部生成提示和异常回答污染 Redis 对话上下文。
2. 控制交给答案模型的工具上下文规模，同时保留各任务的核心事实、来源和错误状态。
3. 明确约束 Markdown 输出：表格最多六列，必须具有非空表头和合法分隔行；无法可靠输出表格时使用列表。
4. 在答案进入 MongoDB 和前端之前检测明显的 Markdown 损坏、重复退化与疑似截断。
5. 首次答案不合格时最多自动重写一次；重写仍失败时返回安全、可读的降级答案，不返回乱码。
6. 全程保留工具调用明细与知识来源，不因答案降级丢失已成功取得的数据。
7. 增加不记录正文的诊断日志，便于按 traceId 定位质量失败原因和重试结果。

## 验收标准

- MongoDB 中已出现的真实异常回答会被质量检测拒绝。
- 合法中文 Markdown、合法 GFM 表格、普通代码块和行内代码不会被误判。
- 首次生成合格时不产生额外模型调用。
- 首次生成不合格时仅重写一次，重写指令禁止表格并要求使用短列表。
- 二次生成仍不合格或抛出异常时，返回确定性的安全降级文本，并保留工作流工具调用记录。
- 工具上下文有明确总预算和单任务预算；裁剪行为可观测且不会抛出异常。
- 工作流答案生成不使用用户会话的 ChatMemory。
- 诊断日志包含 traceId、executionId、答案长度、失败规则和尝试次数，不包含完整 Prompt、工具结果或回答正文。
- 相关后端单元测试、编译及前端生产构建通过。

## 非目标

- 本次不强制更换当前模型供应商或模型名称。
- 本次不把全部自然语言回答改造成固定 JSON Schema。
- 本次不尝试自动修复任意 Markdown，也不对普通对话和 RAG 非工作流回答增加同样的重试链路。
- 本次不改变现有工具接口、MongoDB 文档结构或前端消息协议。
