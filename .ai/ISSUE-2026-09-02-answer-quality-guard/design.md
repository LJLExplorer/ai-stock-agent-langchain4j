# 工作流答案质量防护设计

## 方案选择

采用“上下文预算 + 专用无记忆生成器 + 后端质量闸门 + 单次重写 + 确定性降级”的组合方案。模型升级作为独立的质量优化手段，不作为正确性保障。

未选择仅依赖 Prompt 或更换模型，因为二者无法保证不再出现退化输出；暂不采用完整 JSON Schema，因为改造范围和回答表达约束明显更大。

## 组件设计

### 专用答案生成器

新增仅服务于工作流最终答案的 AiService 接口，由 `AgentConfig` 使用现有追踪模型创建，但不配置 `ChatMemoryProvider` 和工具。`WorkflowAnswerGenerator` 通过该接口生成答案，避免把包含完整工具结果的内部提示及异常响应写入用户短期记忆。

生成接口区分首次生成和重写。首次 Prompt 要求先结论后依据，表格最多六列且必须符合 GFM；无法满足时使用列表。重写 Prompt 接收问题、受预算约束的可信上下文及失败原因，明确禁止表格和代码块，只允许短标题与列表。

### 上下文预算

新增纯 Java 的上下文构建组件，从 `ExecutionState` 的任务历史构建答案上下文。它为整体和每个任务设置字符预算，始终保留任务类型、执行状态、错误信息和最新结果；超出预算时按任务公平裁剪并附加明确的“内容已截断”标记。

首版不解析或重组每一种工具 JSON，以降低耦合；通过总预算、单任务预算和结果历史上限解决无界增长问题。预算使用配置项并提供保守默认值，测试覆盖中文和多字节内容。

### 答案质量闸门

新增无副作用的 `AnswerQualityGuard`，返回是否通过及稳定的原因码。检测规则采用高置信度启发式，避免把写作风格误当故障：

- 空白答案；
- 三反引号代码围栏未闭合；
- GFM 表格表头、分隔行或数据行列数明显不一致；
- 单行存在异常数量的管道符、反引号或表格分隔片段；
- 短窗口重复率过高，表现为标点或片段持续循环；
- 结尾停留在表格分隔符、代码围栏或明显未完成结构中。

合法表格、代码块和包含少量特殊字符的普通文本必须通过。质量闸门只决定接受、重写或降级，不尝试猜测并修补损坏的数据。

## 数据流

```text
成功任务结果
  -> 答案上下文预算化
  -> 无记忆答案模型首次生成
  -> AnswerQualityGuard
       -> 合格：格式化并保存
       -> 不合格：记录原因，禁止表格重写一次
            -> 合格：格式化并保存
            -> 不合格/异常：确定性安全降级
  -> ChatService 保存 MongoDB
  -> 前端 ReactMarkdown 展示
```

## 错误处理与可观测性

首次调用异常与质量失败走同一个有限重试入口，但总尝试次数不得超过两次。重写异常或二次质量失败不再调用模型，改由后端生成简洁降级文本，说明答案摘要生成异常、列出已完成和失败的任务，并提示查看工具明细。

日志记录 `traceId`、`executionId`、attempt、答案长度、上下文长度、质量原因码以及是否降级。日志不记录模型正文、原始工具结果或密钥。上下文发生裁剪时记录各任务裁剪数量，便于后续调参。

## 模型升级关系

更强模型通常能提高指令遵循、Markdown 合法率和长上下文稳定性，因此可以降低首次失败率和重写成本。但模型升级不能替代质量闸门：供应商变更、模型版本漂移、输出上限和偶发退化仍可能产生同类问题。该设计允许以后只改模型配置，不改防护链路。

## 测试设计

- `AnswerQualityGuardTest`：使用 MongoDB 中的真实异常样本作为 RED 用例；覆盖合法 GFM 表格、列表、代码块、行内代码、空白、未闭合围栏、列数不一致及重复退化。
- 上下文构建测试：覆盖总预算、单任务预算、任务公平性、历史结果和截断标记。
- `WorkflowAnswerGeneratorTest`：覆盖首次成功、不合格后重写成功、首次异常后重写、二次失败确定性降级，以及最多调用两次。
- 工作流/ChatService 回归测试：验证最终答案和工具调用仍按原协议返回，生成链路不依赖 ChatMemory。
- 验证命令包括定向单元测试、后端编译、完整可运行测试集、前端生产构建和 `git diff --check`。
