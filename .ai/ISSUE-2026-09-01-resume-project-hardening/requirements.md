# 简历项目工程化整改需求

## 背景

当前项目已经实现股票研究 Agent、Plan-and-Execute 工作流、混合检索、分层记忆、Checkpoint 和全链路日志，具备简历项目所需的技术深度。但公开仓库仍存在工程资产污染、默认测试不可稳定执行、配置不可复制、缺少持续集成和 README 证据链不足等问题。这些问题会削弱面试官对项目真实性、完成度和工程能力的判断。

## 目标

将项目整理为同时适合 Java 后端、AI 应用/Agent 和校招通用岗位的公开简历项目：核心亮点必须能被源码、测试和运行方式验证；仓库默认路径应清晰、可复现、无敏感信息；README 能够解释关键设计取舍，而不是仅罗列功能和技术栈。

## 功能性需求

1. 保留并准确呈现现有核心能力：
   - LangChain4j Agent 与受限工具调用；
   - LangGraph4j Plan-and-Execute 状态图；
   - Milvus Dense + BM25 + RRF 混合检索；
   - Redis 短期记忆、递归摘要与 MongoDB/Milvus 长期记忆；
   - 工作流 Checkpoint、重试、反思和可观测日志。
2. 提供不泄露密钥的配置模板，明确必需与可选依赖。
3. 提供可复现的本地基础设施启动方式和健康检查路径。
4. 默认单元测试不得依赖真实 MongoDB、Redis、Milvus 或外部模型服务。
5. 依赖外部基础设施的测试必须与默认单元测试分层，并明确执行方式。
6. GitHub 持续集成至少验证后端单元测试、前端构建和基础仓库质量。
7. README 必须覆盖项目价值、架构、核心链路、关键设计取舍、容错策略、测试证据、启动步骤、接口示例和面试边界。

## 工程质量需求

1. 移除或停止跟踪与项目交付无关的 IDE、Agent 技能和本地工具资产，恢复准确的语言统计。
2. 修复明显命名错误、重复依赖、无意义测试输出、历史 BUG 编号注释和不一致的依赖注入风格。
3. 不夸大生产能力：尚未实现的鉴权、高可用、性能数据或投资预测准确率不得写入 README。
4. 日志不得默认鼓励记录密钥或无限制暴露用户问题、检索上下文和工具返回。
5. 所有新增配置均使用环境变量或安全默认值，不提交真实凭据。
6. 保持现有公开 API 和核心业务链路兼容，避免为展示效果进行无必要架构重写。

## 验收标准

1. `mvn test` 在不连接外部基础设施的环境中通过。
2. 外部服务集成测试具有独立、显式的执行入口。
3. `npm run build` 在 `frontend` 目录通过。
4. Maven 依赖中不存在当前已知的重复声明。
5. GitHub Actions 工作流覆盖后端测试和前端构建。
6. 仓库提供脱敏配置模板及基础设施编排文件，README 中的命令与文件一致。
7. `git diff --check` 通过，仓库不再跟踪明确无关的本地资产。
8. README 中每项主要技术亮点均能定位到真实实现或测试，且包含项目边界说明。

## 非目标

- 不实现真实证券交易或下单能力；
- 不宣称投资建议或收益保证；
- 不在本轮引入完整用户认证、权限系统和云上生产部署；
- 不为追求技术栈数量替换当前已工作的核心框架；
- 不提交任何本地密钥、Cookie、数据库数据或运行日志。
