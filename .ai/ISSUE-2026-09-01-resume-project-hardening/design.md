# 简历项目工程化整改设计

## 方案选择

采用“全面工程化整改”方案：保留现有 Agent、RAG、记忆和工作流架构，集中补齐仓库卫生、构建复现、测试分层、持续集成、代码观感和项目叙事。相比只改 README，该方案能让文档声明获得代码与自动化验证支撑；相比架构重写，它更符合 YAGNI，并降低引入新缺陷的风险。

## 一、仓库边界与公开展示

公开仓库只保留构建、运行、测试和理解项目所需的资产。停止跟踪 `.agents/`、`.claude/`、`.idea/` 等本地工具或 IDE 内容，并在 `.gitignore` 中明确忽略。检查根目录中的本地配置、日志、生成物和工具配置，避免它们进入后续提交。

补充 License、GitHub Actions 和必要的仓库说明文件。仓库简介、主题等远程元数据不由本次代码提交自动修改，但会在交付说明中给出推荐值。

## 二、配置与可复现运行

从本地 `application.yml` 提炼出脱敏的 `application.example.yml`，所有模型、数据库、Redis、Milvus、飞书和新闻服务凭据通过环境变量注入。配置按“基础对话必需”“RAG/记忆可选”“第三方数据源可选”分组，README 给出最小启动与完整能力两条路径。

提供 Docker Compose 启动 MongoDB、Redis 和 Milvus 等本地基础设施。应用本身继续支持 Maven 直接启动，避免把开发体验强绑定到容器。健康检查用于确认后端可用；外部模型与数据服务是否配置由文档明确说明。

## 三、测试分层与持续集成

默认 `mvn test` 只运行可离线、可重复的单元测试和使用 Mock 的组件测试。当前直接启动 Spring 上下文并访问真实 MongoDB/Milvus 的连接验证测试改为显式集成测试，使用命名约定或 Maven Profile 隔离，避免面试官或 CI 在无基础设施时得到大量错误。

为 JDK 21 下 Mockito/Byte Buddy 的运行方式提供稳定配置，避免依赖 JVM 自附加行为。修复空壳测试、控制台打印和明显失效的断言。CI 分为后端与前端任务：后端使用固定 JDK/Maven 缓存运行测试，前端使用锁文件安装依赖并构建。外部服务集成测试不在无凭据的公共 CI 中伪装执行。

## 四、代码质量与风险控制

将误拼写的 `memoery` 包迁移为 `memory`，同步更新引用和测试。清理 `pom.xml` 重复依赖与临时注释，优先将明显的字段注入调整为构造器注入，但不为了形式统一大规模改写低风险代码。

审查请求参数校验、异常响应、日志内容和外部 HTTP 调用边界。保留有明确业务意义的降级策略，同时避免吞掉无法诊断的异常。涉及用户问题、长期记忆和检索上下文的完整日志应通过配置显式开启，并在 README 说明隐私边界。

## 五、README 信息架构

README 面向首次浏览仓库的面试官，采用以下顺序：

1. 一句话定位与解决的问题；
2. 可验证的核心亮点，而非技术栈堆砌；
3. 系统架构和一次请求的端到端链路；
4. Plan-and-Execute、混合 RAG、记忆系统、可靠性与可观测性的设计取舍；
5. 快速开始、完整环境和配置矩阵；
6. 测试分层、CI 状态与运行命令；
7. API/演示示例、项目结构和扩展点；
8. 已知边界、投资风险声明和面试追问提示。

README 只陈述当前代码可证明的事实。测试数量、性能指标和效果数据只有在可自动复现后才展示，避免用无法解释的数字制造反效果。

## 六、验证策略

按风险从小到大验证：

1. Maven 编译与单元测试；
2. 前端锁文件安装和生产构建；
3. 配置模板语法与 Docker Compose 配置解析；
4. GitHub Actions 语法和仓库跟踪文件检查；
5. README 命令、路径、端口与真实代码交叉核对；
6. `git diff --check` 和最终变更审查。

若本机缺少 Docker 或外部服务，仅验证配置解析和离线测试，并在交付中明确未执行的集成验证，不以“预计可用”冒充结果。

## 七、兼容性与回滚

核心 API、数据集合名和外部工具协议保持不变。包名迁移属于源码级变更，编译器会暴露遗漏引用；配置模板是新增文件，不覆盖用户本地 `application.yml`。仓库资产清理通过 Git 删除实现，可从历史提交恢复，但不影响本地被 `.gitignore` 排除的个人文件。
