## 二、修复方案

### B001: deleteDocument数据不一致

**根本原因**: 向量删除和MongoDB删除无事务保障

**修复策略**:
- 采用"先查询-后删除"的二阶段删除
- 实现RollbackHelper在删除失败时恢复MongoDB记录
- 添加重试机制和告警日志

**改进点**:
```
原流程: 查询 -> 删除向量(可能失败) -> 删除MongoDB(成功)
新流程: 查询 -> 标记为删除中 -> 删除向量(重试3次) -> 删除MongoDB -> 清除标记
```

---

### B002: processAndStoreDocument无异常处理

**根本原因**: 逐个向量添加时缺少容错机制

**修复策略**:
- 实现部分失败处理：记录失败的segment索引
- 添加补偿逻辑：清理已添加的向量
- 返回结果包含成功/失败的vectorIds

**改进点**:
```
原流程: for segment -> embed -> add(失败时直接抛异常) -> 后续segments忽略
新流程: for segment -> embed -> add(失败记录) -> 收集失败索引 -> 补偿删除已添加向量 -> 抛异常
```

---

### B003: syncFeishuDocument并发问题

**根本原因**: 无乐观锁机制，并发读-改-写冲突

**修复策略**:
- 在KnowledgeDocument加version字段的@Version注解
- 使用MongoDB的findAndModify原子操作
- 并发冲突时重试或抛出异常

**改进点**:
```
原流程: 读version -> 修改 -> save(覆盖)
新流程: 读version -> 修改 -> save(version不匹配则失败) -> 重试或报错
```

---

### B004: factCheck置信度逻辑错误

**根本原因**: 无检索结果时置信度设为0.5是错误的

**修复策略**:
- 无检索结果时置信度为0
- 有检索结果但无匹配时置信度为0.3
- 有匹配时置信度 = (matchCount / totalCount) * 0.7 + 0.3

**改进点**:
```
原: confidence = empty ? 0.5 : min(1.0, matchCount/size + 0.3)
新: confidence = empty ? 0 : (matchCount > 0 ? (matchCount/size)*0.7 + 0.3 : 0.3)
```

---

### B005: addDocument无空值验证

**根本原因**: Controller层未验证输入参数

**修复策略**:
- 添加@Valid + 自定义验证注解
- Controller层检查title/content非空
- 返回400 Bad Request而非500

**改进点**:
```
原: 直接传入 -> 业务层NPE -> 500错误
新: 验证层检查 -> 400错误 + 明确错误消息
```

---

### B006: ragQuery无降级方案

**根本原因**: RAG模块异常直接导致整个请求失败

**修复策略**:
- try-catch RagPipelineService.executeRag()
- 失败时返回空的knowledgeSources
- 仍走正常对话流程

**改进点**:
```
原: ragQuery失败 -> 整个chat失败 -> 500
新: ragQuery失败 -> log告警 -> 空knowledgeSources -> 继续对话
```

## 三、核心改进点

### 3.1 数据一致性保障

**方案**: 引入DocumentOperationContext事务上下文
- 记录所有数据库操作
- 失败时自动回滚
- 成功时提交

### 3.2 并发控制

**方案**: 使用乐观锁模式
- MongoDB @Version注解
- FindAndModify原子操作
- 冲突时自动重试（可配置）

### 3.3 容错能力

**方案**: 多层级降级
- 向量存储失败 -> 清理已添加数据 -> 返回业务异常
- RAG检索失败 -> 无知识源对话 -> 用户透明
- API参数错误 -> 400 Bad Request -> 明确错误提示
